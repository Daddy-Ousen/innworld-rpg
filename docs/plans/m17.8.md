# M17.8 Hidden XP — plan

Status: DONE (2026-09-30). Two changes to this plan while building: the fight keeps `peak` and `low` (not `low` alone), so a fight that starts hurt counts only what it took; and the level curve was NOT retuned (a global change cannot close the fighter-vs-worker gap). Both in ADR 0027 "M17.8". Choices approved, see "Answers". Branch `claude/kind-feynman-y4x1mm` restarted from main ff7d757 after PR #86 merged.

Roadmap: `docs/ROADMAP.md` M17.8. Rules: ADR 0022, ADR 0027 "M17.7", user rules in the roadmap entry.
The player never sees any of this: no number, no message.

## What I checked (facts, not guesses)
1. XP has one writer: `Actions.perform` (`xp = base x intensity x risk x novelty x conviction x outcome x skill`).
   Fight XP comes only from `Combat.end_fight`: `attack_melee`, `block_attack`, `throw_object`, `cast_spell`,
   `flee_danger`, `spare_foe`. So one fight-wide factor covers every fight record.
2. Damage to the player has one entry: `Combat.damage_player`. Three callers: monster hits (`combat.gd`), a hostile
   NPC's hits (`brawl.gd`), and traps (`traps.gd`). Traps must NOT count ("foe damage only"). Cold (`winter.gd`),
   hunger and healing use `set_hp`, so they never touch it.
3. **A canon flag cannot mark the Skinner nights.** Probe (seed 1, canon run): `skinner.awake`, `skinner.hunts_the_inn`
   and `skinner.dead` are all still false on the morning of day 39 and all true on the morning of day 40. The events
   resolve in the night, together. So while the player stands in the siege (day 39 evening), no flag exists yet.
   What does exist: the event is still PENDING, inside its day window (39-40), and the stage hours (18-23) hold.
   That is how `Stage.is_open` already decides. The window must key on a pending event, not on a flag.
4. `sim_balance_progress` plays inn work only (no fights, days 1-22). Fight duress does not change it, and the Skinner
   window (days 39-40) is outside it. The pace of a fighter needs its own probe.
5. Only `sim_balance_progress` asserts levels, so few sims should break from the lower fight XP.

## Design

### A. The factor order
`xp = base x intensity x risk x novelty x conviction x outcome x skill x duress x window`.
`Xp.compute` gets two new arguments at the end, default 1.0 (old calls keep their result). The record keeps
`duress` and `window` next to the other factors. No save change for the log: old records simply lack the keys
and nothing reads them after the record is made (only the debug console prints a record).

### B. Duress for fights
- New field `low` in `CombatState.fight`: the lowest HP of the player after a FOE hit, in per mille of max HP
  (integer, so saves and rolls stay exact). `-1` = no foe hit yet. `Combat.damage_player(gs, db, amount, from_foe = true)`
  updates it; traps pass `false`. Healing in the fight never raises it (it is a minimum).
- `Xp.duress_mult(low_permille, rules)`: `lost = 1 - low/1000` (0 when `low` is -1).
  Curve (first setting, see question 1): `x0.5` at 0% lost, straight line to `x1.0` at 10% lost,
  then `+0.01` per 1% more, capped at `x2.0`. Numbers live in `rules.xp.duress`
  (`floor`, `even_at`, `per_percent`, `cap`), not in code.
- `Combat.end_fight` computes it once and passes it to every record of that fight (`opts.duress`). A knock-out is
  100% lost; its `fail` outcome (x0.5) still applies.
- Ally-heavy stages where the player is never hit give x0.5. That is the rule the user chose.

### C. Event windows
- Canon event key `xp_window`: `{"boost": 1|2|3, "hours": [from, to]}` (`hours` optional, may wrap past midnight,
  same test as `MonsterSim.in_hours`). `rules.xp.boosts` maps `1 -> 1.5`, `2 -> 2.0`, `3 -> 3.0`
  so content never holds a raw multiplier.
- A window is active when its event is PENDING (or staged and not yet resolved), today is inside
  `earliest .. latest`, and the hour is inside `hours`. When two windows are active, the highest boost counts
  (they do not multiply each other). It applies to ALL actions, anywhere.
- New module `core/xp_window.gd` (`mult(gs, db)`): reads `db.canon.events` that have `xp_window` (a list built once
  at load). Pure function of `GameState`, so it is deterministic and needs no save data.
- First data (Book 1): `xp_window {boost 2, hours [18, 6]}` on `b1.skinner_leads_the_dead_into_liscor` (gate,
  day 39-40) and `b1.rags_kills_skinner` (the inn fight). Both are pending through the Skinner night.
- Validators: `DataDb/CanonDb` and `tools/validate_data.py` accept the new optional key and check the boost id,
  the hours and that the event is not `alt_only`.

### D. The level curve
After A-C, a probe plays a fighter for ~22 days (Goblins on the Floodplains, sleeping in between) and logs class,
level and HP by day. I compare it with the inn worker (`sim_balance_progress`). If the fighter is far off
(first class after night 3, or level 5 before day ~14 or after day ~28), I change `rules.levels`
(`base_xp`, `growth`, `late_growth`) and report the new numbers. The probe is a loose-assert sim, like the
other `sim_balance_*` scripts.

## Risks
- **Clean wins pay least.** A fight with no HP lost gives x0.5. The cover and position rules (M17.6) reward exactly
  that play, so the two systems pull against each other: a careful player levels at half speed. This is the user's
  rule (canon: the System pays for danger). The `floor` is data, so it can be retuned without code.
- Variance: `risk_mult` (x1 to x4) x duress (x0.5 to x1.9) x outcome (x0.5 to x1). One fight can pay 15 times
  another. The curve should be checked by the pace probe, not by feel.
- A player can raise duress only through foe hits. Cold, hunger and traps do not count, so there is no cheap way to
  farm it. Dropping block or cover on purpose is possible and is a real cost (HP), so I accept it.
- The user cannot see the System's XP. Only tests and the debug console show the factors.

## Questions for the user (asked 2026-09-30)
1. Duress curve.
2. Window and duress: multiply or take the higher.
3. Where windows live: on the canon event or in a list in `rules.json`.
4. Save: no version change (tolerant read) or v21 with a migration.

## Answers (user, 2026-09-30)
1. **Curve:** 1 point = 0.01, straight line. x0.5 at 0% lost, x1.0 at 10% lost, then +0.01 per 1%. A knock-out (100% lost) = x1.9. The x2.0 cap
   stays as a safety for later sources. Floor, slope and cap are data (`rules.xp.duress`).
2. **Stacking:** window and duress **multiply** (best case x3.8 on a knock-out on a x2 night). Two windows at once: the highest boost counts.
3. **Window data:** on the canon event (`xp_window`, next to `stage`); `rules.xp.boosts` maps the tier to the multiplier.
4. **Save:** "I don't care about old saves. No one besides me played the game." So NO version change and no migration. `CombatState.fight["low"]`
   is read with a default (-1 = no foe hit yet). Rule 8 in CLAUDE.md asks for a migration on a schema change; the user waived it for this field
   (noted in ADR 0027 "M17.8").
