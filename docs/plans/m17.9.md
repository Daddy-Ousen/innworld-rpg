# M17.9 XP for non-fighters (plan, 2026-10-05, cloud)

Status: built 2026-10-05 (ADR 0027 "M17.9"). User answers: work duress in data; level 5 by night 9 – 10; crowd and cold.
Changes from the draft: the cold is a 0 / 1 context value (Winter.status), not a share; `tools/validate_data.py` does not read
action shapes, so the check is only in `DataDb` (the load check every run uses).

## Problem
The pace probes of M17.8 (ADR 0027 "M17.8") measure this:
- Fighter (`sim_balance_fighter`, two Goblin fights a day): total level 5 on night 6 – 7.
- Inn worker (`sim_balance_progress`, a full 9-hour inn day): total level 5 on night 14.

DESIGN §1 says "A non-fighter must be able to progress." The core of this game is the inn. So the gap works
against the main loop.

## Root cause
1. **Risk.** `risk_mult = 1 + 3 × risk`. Fight actions have risk 0.4 – 0.5 (x2.2 – x2.5). Every inn action has
   risk 0 (x1.0). Risk is the largest single factor, and only fights get it.
2. **Duress.** M17.8 added a hidden duress factor (up to x2.0), but only fights set it. Work always pays x1.0.
3. **Time.** Fight records cost 0 game minutes (`Combat._record`). Two fights take a few minutes of the day.
   The worker's XP costs about 9 hours. So per game hour the gap is far larger than 2 : 1.

A global curve change does not help. M17.8 measured it: `base_xp` 52 slows both sides and keeps the 2 : 1 gap.

## Approach (recommended): work duress, in data
A hard working day pays more than an easy one, like a hard fight pays more than a clean win.

- `data/actions.json`: an action may carry an optional list `duress`. Each entry reads one context key and rises
  in a straight line: `{"key": "guests", "from": 5, "to": 20, "max": 1.8}` gives x1.0 at 5 guests or fewer, x1.8 at
  20 or more. Several entries multiply. The result is capped at `rules.xp.duress.cap` (2.0).
- **No floor below x1.0 for work.** An empty inn pays the plain XP of today. So the worker's present pace is the
  minimum. (Fights keep their x0.5 floor.)
- `Actions.perform`: when the caller passes no `opts.duress`, it computes the work duress from the action's list
  and the context. Fights keep passing their own value, so fight XP does not change.
- The record already keeps `duress` (M17.8). **No save change**, no migration.
- Context sources: `guests` already reaches cook and serve actions (`Interact.perform`, `Guests.serve`). `cold`
  is new: `Winter` writes the share of cold the player is in when the action starts (0 – 1).
- The player never sees any of it (ADR 0022). The debug console record shows the factor, as for fights.
- Checks: `DataDb` / `ActionDb` load check and `tools/validate_data.py` check the shape (key, from < to, max >= 1).

This is a schema change to `actions.json` (an optional key). CLAUDE.md rule 11 says ask first: this plan asks.

## Rejected
- **Raise the base XP of inn actions.** It needs no code, but it is blunt. An empty inn at 3 a.m. then pays the
  same as a dinner rush with 20 guests. "You level by living" (DESIGN §1) asks the hard day to pay more.
- **Give work actions risk.** Risk means danger. A dinner rush is hard, but it is not dangerous. That would put
  false meaning in the data.
- **Slow the fighter.** M17.8 found the fighter pace fair. Lowering it only moves the problem.
- **Hunger as a source.** If acting hungry paid more, the best play would be to starve yourself. That rewards
  neglect. Leave it out.
- **Wounded patients (healer).** Bandage heals only the player. No mechanic for treating others exists yet.

## Open choices (for the user)
1. Approach: work duress in data (recommended), or raise base XP (data only).
2. Target pace for a busy inn worker (guests rise from 2 to 20 over the days): level 5 by night 9 – 10
   (recommended: the fighter keeps a small lead for the danger), or full parity (night 6 – 7).
3. Sources in this step: guests (crowd) for cooking and serving (recommended), cold for travel, running and
   hauling (recommended), and more XP windows for the big nights of Books 1 – 6 (data only).
