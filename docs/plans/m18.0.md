## What I checked (facts, not guesses)
1. `CanonDb._build_order` is a Kahn sort. Among ready events it picks the lowest `window.earliest`, then the lowest id.
   The director walks `canon.order` every night (`Director._run_day`); `Brawl` also walks it. Nothing else sorts events.
2. Every event id in Books 1 – 5 starts `b<N>.` (151 + 207 + 157 + 111 + 140). For one-digit book numbers, "book number,
   then id" sorts the same as "id". So a book tie-break does not change the Books 1 – 5 order.
3. Chapter files are read in file-name order, and Godot and Python keep JSON key order. "Place in the file" is stable.
4. The validator (`tools/validate_data.py`) allows only `schema_version, book, chapter, events, system` at the top of a
   chapter file. `order` must be added there.
5. Laken's thread: 16 Book 3 events (3.00 E, 3.01 E, 3.11 E, 3.12 E, 3.14) and 15 Book 5 events (4.20 E – 4.23 E).
   Each `canon_ref.note` gives his journal day. Book 4 Laken events (days 93 – 96) do not move.
6. Flag links after the move: only one non-Laken event needs a Laken flag: `b4.laken_says_enough_in_invrisil` (day 93)
   needs `laken.left_for_invrisil`, now set on day 91. It still holds. No Laken event needs a flag that comes later.
   No Laken event clears a flag. (Script check over every event, 2026-10-01.)
7. An event fires on the first night with `earliest <= day` and no failed check. `latest` only sets how long it may
   wait. So a wider window changes nothing in a canon run; it gives slack when a check fails.

## Design

### A. Chapter order (answer 1)
- A chapter file may have `"order": <int>` at the top (its place in the book; 1, 2, 3 …; unique in the book).
- `CanonDb.load_root` records, for each event, `rank[id] = [book, order, place]`:
  `book` = the file's `book` key, `order` = the file's `order` (0 when missing), `place` = the event's index in the
  file's `events` object, **but 0 when the file has no `order`** (so the id still breaks the tie, as today).
- `CanonDb.from_dicts(npcs, locations, events, rank = {})`. Toy dbs pass no rank: rank `[0, 0, 0]` for every event,
  so the old rule (earliest, then id) holds.
- `_before(a, b)`: earliest, then `rank` (book, order, place), then id. `depends_on` still comes first (Kahn).
- No save change: the order is built at load and never saved.
- Validator: `order` is optional, a whole number >= 1 (not a bool), unique in a book. A book where some chapter files
  have `order` and others do not gets a **warning** (not an error): the unordered events would sort before the
  ordered ones of the same day, by id. (The user approved the key, not an all-or-none rule; a warning stays inside that.)

### B. Laken's calendar (answer 4): game day = journal day + 45
- `earliest` = first journal day + 45, `latest` = last journal day + 45 (a note "Day 34-38" gives 79 – 83). The window
  `confidence` stays `guess`. The note's "Placeholder day" text becomes "Game day = his Day + 45 (ADR 0028)".
- Ids do not change (event ids are in saves).
- An old save in the middle of Book 2 or 3 has Laken events still pending with an earliest day that is now in the past.
  They fire on the next night, in chain order (the director loops a night until nothing more fires). No migration.
