## Engine finding: event order inside a day
`CanonDb._build_order` sorts events by `depends_on`, then `window.earliest`, then **id**. To keep the book's order
inside one day, Book 5 put letters in front of its ids: 115 of its 140 event ids start `b5.z…`
(`b5.zzzzza_…`). Ids are hard to read, and a new event in the middle means renaming others. Using `depends_on` for
order is wrong too: a cancel then spreads to every later event. Book 6 has nine dense Liscor days, so this gets
worse. **Answer: a chapter order number** (M18.0, below).

## Answers (user, 2026-10-01)

   This is a JSON schema change (rule 11): asked and approved here.
2. **New maps: Wirclaw's village, the crypt ossuary, the inn basement.** No Liscor sewers (the text only
   mentions those jobs).
3. **The attack on Esthelm is a wave stage** at `esthelm_ruins` on the night of about day 117: Goblin Lord troops

4. **Laken's journal (changed 2026-10-01): game day = Laken day + 45, in every book, no squeeze.** The first answer

## M18.0 Canon timing (2026-10-01, built)
Plan: `docs/plans/m18.0.md`. Answers 1 and 4 above; no new choice was needed.

**Event order.** `CanonDb.load_root` records `rank[id] = [book, order, place]` for each event: the file's `book`, the
file's `order` (0 when missing) and the event's place in the file (0 when the file has no `order`, so the id still
breaks the tie). `_before` sorts by `depends_on` (Kahn), `window.earliest`, `rank`, then id. Toy dbs
(`from_dicts` without a rank) keep the old rule. The order is built at load and is never saved: no save change.
- The book number also fixes a latent trap: an id sort puts `b10.` before `b9.`.
- Books 1 – 5 have no `order`. `unit_event_order` checks that their run order is the same as the old rule
  (earliest, then id) on the real data. That check stays valid when Book 6 adds ordered chapters: books without
  `order` never depend on later books, so their part of the order cannot change.
- A bad `order` (not a number >= 1) is a load error and counts as no order. The validator checks: whole number
  >= 1, not a bool, unique in a book. A book that mixes files with and without `order` gets a **warning**, not an
  error (the user approved the key, not an all-or-none rule): the unordered events of a day would run first, by id.

**Laken's calendar.** 16 Book 3 events (3.00 E – 3.14) and 15 Book 5 events (4.20 E – 4.23 E) moved to his
journal day + 45. A note range ("Day 34-38") became the window range (79 – 83); an event fires on the first window
day when it is ready, so the range only adds slack. The window `confidence` stays `guess`. Ids did not change
(they are in saves). A no-input run fires every one of them on its first window day, drift 0 to day 115 (a throwaway
probe, not committed).
- Only one other event needs a Laken flag: `b4.laken_says_enough_in_invrisil` (day 93) needs
  `laken.left_for_invrisil`, now set on day 91.
- An old save from Books 2 – 3 can have Laken events still pending with a first day now in the past. They fire on
  the next night, in chain order. No migration.
- Tests: `sim_canon_book3` keeps its Liscor end (day 87) and then runs Laken's thread on to day 91
  (`LAKEN_LAST_DAY`); `sim_canon_book5` ends on day 115 (was 118). ADR 0016 and ADR 0020 point here.
